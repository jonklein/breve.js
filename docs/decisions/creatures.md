# Evolved creatures: where the genome lives and who runs the population

**Context.** The demo is Karl Sims' creatures (1994): bodies and neural brains that evolve together, many creatures tried side by side. It forces four questions the spec left open.

**1. Who runs a population?** Options: (a) many creatures in one world; (b) a sub-sim per creature, run by a program above them; (c) put it in the experiment runner. Chosen: (b). A population in one world makes creatures collide and share terrain, which spoils a fair test, and one physics world cannot take a different body per creature of one set. Sub-sims are what the spec's tree (SPEC 7.1) was for: a parent makes sims, reads their metrics, makes new ones. The experiment runner needs a fixed set of numeric params and ends with a table, so it does not fit a genome that changes shape. The new `parent` export (`Parent`, `ParentHost`, `ParentRun` in core) is small: `init`, `step`, `status`, and a host with `add`/`remove`/`group`/seeded random. The workbench shows the group as tiles (the existing sweep view); a headless run uses the same `ParentRun`. Evolution itself is the example's code, not the core's.

**2. How does a sub-sim receive its genome?** Options: numeric `params` (hundreds of weights as sliders), a message from the parent at tick 0 (the body is needed at build time, so it cannot carry the body), a closure in the script (cannot be serialized to a worker or a share link), or a structured field in the scene. Chosen: scene `data`, plain JSON, read as `ctx.data`. It is part of the scene, so it is saved, shared, snapshotted with the scene, and valid in workers. The rule of thumb stays: sliders are `params`, structured input is `data`.

**3. How is morphology encoded?** A small version of Sims' recursive graph, kept to a fixed-size list so crossover and mutation stay simple. The body is a trunk (a box) plus up to seven more blocks. A block says which earlier block it hangs from, on which of its six faces, where on that face (two numbers), its size (three numbers), which axis its hinge turns about, whether to repeat it as a mirror image across the body, and whether to continue it as a second, smaller segment. Blocks hang only from earlier blocks, so the result is always a tree; a block whose parent is switched off disappears with it. All boxes and axis-aligned, so no rotations to get wrong. Mirrored blocks pass the mirroring on to their descendants (every relative z offset flips), which gives left/right symmetry without storing it twice. The same few genes can make legs, arms, tails, spines, fins and stacks of lumps; the old fixed "pairs of legs" body is gone. Mutation changes sizes by a factor, moves blocks on their parent's face, re-hangs a block from another, adds or drops blocks. `layout(genome)` places every block standing on the ground and `bodyOf` writes the body the validator checks. Not done: Sims' joint types other than hinges, rotated attachments, and a node being reused at several places (his recursion limit).

**4. How does a brain fit a body that changes?** One fixed network with a slot for every joint a body could have (28: seven blocks, two sides, two segments): inputs are those joint angles (zero for absent joints), which way is up, and a clock; outputs are joint targets, and only the slots a body has are used. The network therefore keeps its shape while the body changes, and weights can cross between parents. The clock gives it a rhythm to start from.

**Fitness.** A creature scores nothing if it is ever faster than 8 m/s, leaves the terrain or drops below the ground, because overlapping boxes in a random body can make the physics engine throw it (before this guard, scores of hundreds of metres appeared). Otherwise: straight-line distance walked between tick 90 (after landing) and the end of the generation, in any direction (the spawn heading is random). Selection keeps the best few unchanged, breeds the rest by tournament, crossover and mutation. Because sims are deterministic, a kept creature scores the same again, so the best score never goes down (a test checks it).

**Consequences.** `ctx.data` and `self.up` are new script API. A parent script runs on the worker's main loop one tick at a time; a generation swap (a few ms per sim for the physics world) happens between ticks. Physics sub-sims cannot be forked, so clicking a tile starts a fresh run of that creature's scene. Not done: saving the best genome from the page, an embed that runs parents, running sub-sims on several workers (`ParentHost.add` would then take a scene and return a handle), and fitness that rewards anything but distance (by default creatures that roll or tumble forward score like walkers, since tumbling can be a valid strategy; the "reward staying upright" param, 0 to 1, scales a score by the share of the generation spent upright).
